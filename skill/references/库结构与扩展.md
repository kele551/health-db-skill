# 库结构与扩展

> 摘自 `SKILL.md` 正文（2026-11-24 拆分），口径与优先级不变；正文只留指路。

> 前置口径：通用化（`HEALTH_ROOT` / `HEALTH_DB` / `HEALTH_NAME`）、单文件 SQLite 正本、认不准不入表 —— 三条在正文，这里不重复。

### 3.4.1 库怎么扩展（2026-11-15 起写死）
**通用原则（用户 2026-11-15 定：通用型，要适合大部分人的特殊要求）**：

1. **一人一库**：任何人一个新 `.db`，结构同一套（`健康库.init_db`），只换档案卡与数据，不换结构。
2. **新指标优先零建表**：任何别人有的指标（血氧、尿碘、HbA1c、尿酸、肺功能、骨密度……）一律走 `ext_metric`：类别 / 指标 / 数值 / 单位 / 参考区间 / 来源 / 备注。**要显示再决定加列或建表**，不许为了一个人一件事就改结构。
3. **实在要新类别才建表**：表名中性（`sleep_stage`、`med_change`、`mood_score` 这类），不出现人名、病名、药名。
4. **每人自己的口径放档案卡与 `schema.json`**，表结构不带任何人的目标值。

| 要干的事 | 命令 |
|---|---|
| 给已有表补一列 | `python <ROOT>\tools\健康库.py add-column weight waist_cm REAL` |
| 新建一张表 | `python <ROOT>\tools\健康库.py add-table mood_score date:TEXT,score:INTEGER,note:TEXT` |
| 给另一个人建空库 | `python <ROOT>\tools\健康库.py init "D:\<某人>\医疗与运动健康数据库.db" <姓名>` |
| 看库里有哪些表 | `python <ROOT>\tools\健康库.py tables` |
| 看某表有哪些列 | `python <ROOT>\tools\健康库.py columns weight` |
| 往任意表追加一行 | `健康库.append("mood_score", {"date":"2026-11-15","mood":7})`（列名不符直接报错，不静默丢数据） |

- 加列/建表后：① 在 `健康库.py` 补 `load_<表>` 读函数；② 需要的话改 `replace_table` 的列映射（**否则整表写回会丢新列**，这条踩过）；③ 摘要/看板要显示才改模板。
- 扩之前先 `backup_db()`；扩完跑 `counts()` 确认老表行数没变（本人库基线：bp_glu 537 / daily 428 / weight 62 / lab 412 / doc 339 / tcm_prescription 259 / tcm_fee 33 / wearable_daily 54175（视图 wearable_raw 同名可查））。

### 3.4.2 手机厂商导出包（华为运动健康 HUAWEI_HEALTH.zip）入库（2026-11-22 定，同日改口径）

**用户原话**：「所有数据全部录入，不能遗漏」→ 后改为「原始明细表转换成数据就行了，没有必要存在」。两者合起来的口径是：**明细要读全、要算进库，但库里只留「每天×类型×指标 一条」的汇总，不留逐点原表。**

```
python <ROOT>\toolchain\python\envs\default\Scripts\python.exe <ROOT>\tools\华为导出入库.py --zip "<zip 路径>"       # 只预览
                                                                                    --apply    # 真写库（自动 backup_db）
                                                                                    --upload   # 写库后覆盖云盘
```

- **`--dir` 可传任意子目录**：脚本自动上溯到导出根目录，一次读全 `Health detail data & description` / `Sample sequence` / `Motion path` / `Sport per minute` 四批 json（**只读 Health detail 会漏 700xxx 原始序列与逐分钟运动数据**，这条踩过）。
- **落点**：① 三张标准表照 §3.1 口径；② 穿戴数据进 `wearable_daily`（`date/type_code/type_name/metric/n/avg_v/min_v/max_v/sum_v/value/agg/first_at/last_at/sample_text/source`，主键 `type_name+metric+date`）；③ 有临床意义的连续指标按天汇总进 `ext_metric`（类别「穿戴设备」）。
- **为什么不留原表**：150 MB 里 149 MB 是 79 万条逐点明细（动态心率点、睡眠分期、运动心率路径、压力曲线），医疗数据不到 1 MB。压成 51,675 条日后 **12.4 MB**，页面功能和数值全部不受影响（2026-11-22 实测）。
- **聚合口径**：`agg=sum` 用于步数/距离/热量/时长/睡眠类（`STEP|DISTANCE|CALORI|KCAL|DURATION|_MIN|SLEEP|WATER`）；`agg=min` 用于血氧类（取当日最低）；其余 `avg`。`value` 就是按这个规则算出的当日代表值。
- **兼容**：库里有同名**只读视图 `wearable_raw`**（把 daily 表拼回旧列名 `start_time/end_time/text_value/extra`），所有老页面与脚本不用改 SQL；`extra` 里写 `n=… agg=…`。
- **再导入不会重新膨胀**：`健康库.add_raw()` 已改成先按天聚合、再与旧行合并（n 累加、sum 累加、min/max 取极值、first/last 取最早最晚），传入逐点数据也只会落成一行。
- **改判定/聚合逻辑后**：删 `<ROOT>\projects\健康数据\导出\.看板缓存.json` 与 `.总览缓存.json`，重跑 `华为数据总览.py` → `穿戴数据看板.py` → `健康生成器.py 总览`（顺序不能反，看板的类型统计来自总览缓存）。
- **明细纪律**：
  - 一个测量键 = 一行；`accFlag / algorithmVer / timeType / devNo / dataId / version / localDate` 这类算法与容器字段不入明细（`NOISE`）。
  - 二进制原始序列（detailData，含十六进制波形/睡眠 RRI）与逐分钟运动明细**先 zlib 压缩再存 `text_value`**（前缀 `zlib+base64:`），**原文一个字节不丢**、体积约 1/20；要还原就 base64 解码后 zlib 解压。
  - 30001 心率路径按 `tp` 拆行：`k` 是绝对毫秒（≥1e12）直接用、相对偏移（0~3e6）加到记录起点、`p-m / b-p-m` 是每公里配速哨兵值**不拆行**（原文仍在压缩块里）。
  - 运动分钟数据：同一分钟会因合并/更新留下多条，**只取步数最大的一条**再按天合计（全部相加会翻倍）；`duration` 是该分钟记录长度、**不是**锻炼分钟，不入 `exercise_min`。
- **跨源一致性**：手表逐分钟步数约为手机端 `300002` 官方值的 9 成；**官方步数已有值的日子不拿手表数覆盖**（避免「官方 82 步 + 手表 9.7 公里」这种混源行），只补 `daily` 的空字段。
- **xls 只取两张**：`user health daily statistics.xls` / `user health daily samplestat.xls`（官方按天汇总，`type_name=每日汇总(...)`）；其余 80 多张是账号/订单/优惠券/设备/会员表，**不进健康库**。
- **体积与代价**：全量后库约 150 MB（明细 79 万行）；外部存储里的整库随之变大，**每次 `--pull` 要下载整库**。嫌慢可把 `wearable_raw` 拆到独立归档库，标准表保持小库（需用户点头再动）。

**给本人看的两个单文件网页（2026-11-22 用户定「以后所有都生成单文件网页」「这种就看得懂了」）**

```
python <ROOT>\tools\穿戴数据看板.py      # 人话看板：睡眠/静息心率/HRV/血氧/压力/活动/体重 + 哪天有数据
python <ROOT>\tools\华为数据总览.py      # 全量核对页：总量、56 类明细、指标清单（可搜索）
```

- **医疗版 `健康档案看板.py`（2026-11-22 定）**：骨架＝Fasten Health「按身体系统分组 + 病历时间线」＋ Apple 健康摘要的参考区间三段条。每指标一行＝名称 + 最新值 + 区间标尺（指针位置）+ 状态徽章 + 迷你趋势 + 日期，点行展开历史；顶部双来源说明条；导航＝概览 / 体征 / 病历 / 化验 / 时间线 / 原始数据。
  - **双轨判定**：化验按报告单区间；糖化 / LDL-C / TSH / BMI / 血压 / 血糖按本人目标（唯一出处 `<ROOT>\tools\健康目标口径.py`）。`parse_ref()` **只取无符号数字**（报告单写法是 `57--97`、`0--4.11`，带 `-?` 的正则会把上限吃成负数，实测把 16 项正常值判成偏高）；先 `replace("--","-")` 再抽数字。
  - **术后/用药特例**：Tg 低＝治疗目标不判低；FT4 因优甲乐偏高；尿糖阳性来自恩格列净；抗坏血酸阳性无意义。
  - **双来源分层**（用户 2026-11-22 定）：体检组 `SRC_OF` 映射——代谢/心血管/肾脏/甲状腺/肝脏/血液/肿瘤随访＝「医疗」（自己测 + 医院单据）；心率与恢复/睡眠与呼吸/活动量＝「设备」（华为手表手机）。体征页按这两段分开渲染，卡片标题带来源小标。
  - **病历区**：住院与手术（取档案卡 `conditions` 带 `date` 的条目，按日期倒排，标签写入院/出院/手术/门诊/已切除）、复查提醒（`reminders` 的 下次/上次/周期）、影像与病理结论（只抄原文结论）。
  - 缓存 `.医疗看板缓存.json`（键＝库 size+mtime）；改判定逻辑后**先删缓存**再跑，否则读旧结论。
- **两页同一套视觉（2026-11-22 用户定「肯定要统一版式」）**：`摘要模板.html` 的 `<style>` 已换成 `健康档案看板.py` 的同一套色板（`--paper:#fff`、`--desk:#f6f7f9`、`--line:#e4e8ec`、`--calm:#1f5c50`、`--flag:#bf5a2c`），标题不再用宋体、卡片 10–12 px 圆角、`td.hi/lo` 改为淡底+彩字（去掉重描边），内嵌 SVG 与 favicon 同色。**内容分工不变**：摘要仍是 A–E 层 + 一屏结论 + 客观判定，可打印；只动颜色与圆角，**不动 `{{...}}` 占位符**。旧模板备份 `摘要模板-旧版-20261122.html`。
- **统一入口**（`<ROOT>\projects\健康总览\健康生成器.py`）：`摘要` → `_摘要内核` + `_摘要组装.py` + `摘要部件\`，输出 `就诊摘要\<姓名>-就诊摘要.html`（姓名取库 `profile.name` / `HEALTH_NAME`）；`总览` → `<ROOT>\tools\健康档案看板.py`（旧 echarts 内核已归档），输出 `健康总览\健康总览.html`。两页都不依赖 CDN；三处取数统一走 `健康库.py`，不再各自连库。
- **数据库只有一份**（用户 2026-11-22 再确认）：运动健康与医疗健康**同库**（`医疗与运动健康数据库.db`：`wearable_raw` 明细 + `lab/bp_glu/weight/doc/tcm_*` 标准表），页面上的「医疗 / 设备」只是展示分层，不拆库。
- **三个页面都不依赖 CDN**：图表是自写 SVG，离线打开就有图（旧 echarts 版已废弃，断网空图不是没数据）。

- **穿戴数据看板 = 用户认可的口径**：只讲六件事，每块「一句人话结论 + 一张图」；不堆 400 项指标。
  - 睡眠＝近 30 晚堆叠条（深/浅/REM），标 7h 红线；文字给平均时长、深睡占比、低于 6.5h 的晚数、睡眠呼吸暂停风险等级（1–4，越高只是提示去专科查）。
  - 压力**只取白天 08–21 点的「压力指数」**（`start_time` 是毫秒时间戳，要 `fromtimestamp` 换本地小时）；混入「压力等级」或夜间低值会把日均拉到 20 多。
  - 血氧**画夜间最低**（`每日汇总(血氧)` 的 `minSpO2`，过滤 70 以下脏值），文字写「日均 / 夜间最低均值 / 最低值日期 / 低于 90 的天数」；只画日均会是一条平线，看不出掉点。
  - 体重只取 `date >= 2024-01-01`（2019 年的旧点会把折线拉平）。
  - 日历热力＝每天记录条数（几百/上千/几千四档），一眼看出哪段时间没数据。
- 生成器读库 + `.总览缓存.json` / `.看板缓存.json` 缓存（键＝库文件大小+修改时间），库没变二次生成 **0.1–1 秒**；别再用 `row_number()` 或在 79 万行上跑逐指标查询（实测 171 秒）。

### 7.11 daily 表新增 4 列（2026-11-16）

daily 表在末列追加 active_kcal(REAL) / exercise_min(INTEGER) / active_hour(INTEGER) / distance_km(REAL)，记华为运动健康「今日」页的活动热量千卡、锻炼分钟、活动小时数、运动公里。华为今日页这三个实际值是裸数字且 OCR 文本顺序会乱（标签「锻炼/热量/小时」、数字「179/19/10」不对应），脚本用 `activity_from_card()` 几何定位（标签 x 中心配下方最近数字）+ 原图/放大1.5倍两遍一致才采信，单位行「/25分钟 /534千卡 /12小时」是目标值不采信。距离用「N公里」文本锚定。写库链已同步：STANDARD_DDL / upsert_daily / replace_table / load_daily / DAILY_HEADER / merge_daily / parse_daily。今天 2026-11-16 实测：步数3891 睡眠404 热量179 锻炼19 活动10h 距离3.09，历史8行零变化。
